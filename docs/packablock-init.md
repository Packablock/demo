# ⛓️ Packablock Initialization & Onboarding Steps

This document outlines the step-by-step procedure used to onboard and initialize **Packablock Zero-Trust Supply Chain Policy Control** inside this monorepo project.

---

## 💻 Step 1: Install the `pkablk` CLI in the Dev Env

To manage the cryptographic log and check supply chain policies locally, we installed the Packablock CLI (`pkablk`) globally. Since it is hosted directly on GitHub, we pulled the client using Bun:

```bash
bun install -g Packablock/packablock-client
```

This registers the global `pkablk` executable command.

---

## 🏁 Step 2: Run `init` to Bootstrap the Chain

We bootstrapped a new local cryptographic ledger ledger log `packablock.yaml` tracking the project's root workspace lockfile `bun.lock` (which we generated by running `bun install`). 

We executed the initialization command:

```bash
pkablk init packablock.yaml -l bun.lock -d "Initial monorepo supply chain genesis block"
```

This parsed the current dependencies inside `bun.lock`, calculated their cryptographic signatures, and generated the genesis block (Index `0`) inside a newly created [packablock.yaml](../packablock.yaml) file.

---

## 💾 Step 3: Commit the `packablock.yaml` Chain

The generated `packablock.yaml` is the immutable ledger of our dependency history. We added and committed this ledger to the git repository:

```bash
git add packablock.yaml
git commit -m "Initial commit of pristine monorepo demo simulation"
```

Any subsequent changes to the dependency tree will be recorded as new blocks appended to this chain.

---

## 🤖 Step 4: Add Validation and Append to the CI Workflow

To enforce supply chain verification on every contribution, we added a continuous integration workflow in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). 

The pipeline runs on every push and pull request to the `main` branch. It executes the following automated Packablock validation steps:

1. **Install CLI tool globally**:
   ```yaml
   - name: Install Packablock Client CLI
     run: bun install -g Packablock/packablock-client
   ```

2. **Verify cryptographic chain integrity**:
   Runs offline/standalone chain validation to ensure the log history is intact and matches historical signatures:
   ```yaml
   - name: Verify Cryptographic Chain Integrity
     run: pkablk check packablock.yaml
   ```

3. **Audit dependency constraints**:
   Audits the active dependencies and visualizes the drift hierarchy:
   ```yaml
   - name: Audit Dependency Constraints
     run: pkablk audit packablock.yaml --visualize
   ```

4. **Detect and automatically append manifest changes**:
   Compares the active workspace `bun.lock` against the latest chain ledger block and appends a new block if differences are found:
   ```yaml
   - name: Detect and Append Manifest Changes
     run: pkablk append packablock.yaml -l bun.lock
   ```

5. **Enforce ledger synchronization check**:
   If the developer modified `bun.lock` but forgot to run `pkablk append` and commit the updated `packablock.yaml` locally, the CI command `git diff --exit-code` detects the uncommitted changes in `packablock.yaml` and fails the pipeline:
   ```yaml
   - name: Check for Uncommitted Changes
     run: |
       if ! git diff --exit-code packablock.yaml; then
         echo "::error::Local dependencies changed but packablock.yaml was not updated. Please commit the updated packablock.yaml."
         exit 1
       fi
   ```

---

## 🤖 Step 5: Automated Dependabot Lifecycle Management

To keep dependencies updated automatically without breaking our supply chain validation, we integrated **Dependabot** with self-healing log updates.

### 1. Enable Dependabot
We enabled daily scanning for Bun and Python dependencies inside [`.github/dependabot.yml`](../.github/dependabot.yml).

### 2. Auto-Append & Auto-Merge Workflow
Since Dependabot is unaware of our cryptographic ledger `packablock.yaml`, any lockfile updates it suggests will normally trigger a validation failure in `ci.yml`.

To solve this, we created an automated assistant workflow in [`.github/workflows/dependabot-helper.yml`](../.github/workflows/dependabot-helper.yml) that triggers when Dependabot submits a PR. The helper:
1. Checks out the Dependabot pull request branch.
2. Installs dependencies and our client CLI.
3. Automatically runs `pkablk append packablock.yaml -l bun.lock` to record the updates.
4. Commits and pushes the updated `packablock.yaml` back to the Dependabot branch.
5. Approves and configures the PR for auto-merge.

Once the `ci.yml` validation suite finishes verifying the updated branch, GitHub automatically merges the pull request.
